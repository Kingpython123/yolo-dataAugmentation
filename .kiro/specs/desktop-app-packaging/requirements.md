# 需求文档：缺陷合成流水线桌面化封装

## 1. 背景与问题

现有 `yolo-dataAugmentation` 是一个功能完整的 CLI 流水线（11 个子命令，核心生成链路已验证）。
当前的使用方式对协作者有以下摩擦，逐条来自 README 的操作说明：

| 现状 | 摩擦点 |
|---|---|
| `git clone` + `python -m venv` + `pip install -r requirements.txt` | 协作者需自备 Python 3.11 并正确建虚拟环境 |
| 每开一个终端都要 `$env:RELAY_API_KEY="sk-..."` | 易漏、易忘、key 在终端历史里留痕 |
| 数据集必须放在项目上一级、目录名含全角括号 | 路径写错即报“类别无干净图”，定位靠人工比对 |
| 单次跑 3.5~4.5 小时、不能关终端 | 无进程守护、无持久化进度视图，终端一关就丢上下文 |
| 产出需手工挑 `generated/` + `rejected/` + `annotations.jsonl`，且要跳过 `debug/` | 纯手工步骤，容易误带 2GB 的 debug 目录 |
| 失败原因靠 `fail-summary` 翻 jsonl | 需要记住第二个命令 |

本次范围是交付形态的工程化，不是功能变更。生成算法、prompt、质检阈值、缺陷库均保持现有行为不变。

## 2. 目标与非目标

### 目标

- G1 协作者拿到一个安装包，无需安装 Python 或任何依赖即可运行。
- G2 密钥、数据目录、类别、数量等参数通过界面配置并持久化，不再依赖每次设置环境变量。
- G3 长时间任务可视化：实时进度、剩余时间估算、失败计数、可中断、可续跑。
- G4 一键导出符合交付规范的成果压缩包。
- G5 构建过程可复现，任何人在干净机器上执行一条命令即可产出同样的安装包。

### 非目标

- N1 不修改生成算法、prompt 模板、质检权重与阈值。
- N2 不重建缺陷库（`build-catalog` 保持现状，界面上不暴露或需二次确认）。
- N3 不做多机分布式调度、不做用户账号体系。
- N4 不支持 macOS / Linux 桌面分发（如需，仅保留源码 CLI 路径可用）。

## 3. 现状约束（已通过阅读代码核实）

- C1 `src/config.py:10` 的 `PROJECT_ROOT = Path(__file__).resolve().parent.parent` 在冻结环境下指向 PyInstaller 解包目录，`config.yaml`、`outputs/` 定位会失效。代码中不存在 `sys.frozen` / `sys._MEIPASS` 处理。
- C2 `Config.resolve()` 把所有相对路径解析为“相对 config.yaml 所在目录”。冻结后该目录会变成临时目录，必须重定义基准目录。
- C3 项目未使用 `logging`，进度输出为 `print` + `tqdm`，且 `print` 发生在 `ThreadPoolExecutor` 的工作线程中（`src/generate.py` 的 `_synthesize_one` / `_run_tasks`）。GUI 或文件日志需要先建立输出边界。
- C4 `outputs/catalog` 共 676 个文件、约 440 MB，超出合理的单文件 exe 体积，必须外置分发。
- C5 `outputs/catalog/catalog.json` 中部分条目的 `source_image` 为建库机器的绝对路径（形如 `D:\zlf\project\photo_difussion\...`）。因同时存在 `source_size` 字段，当前不影响裁块计算，但属于可移植性缺陷。
- C6 Windows 控制台默认代码页为 GBK，直接读取项目内 UTF-8 中文内容会乱码；打包后的程序必须显式固定 UTF-8。
- C7 运行期依赖：`pillow` `numpy` `opencv-python` `requests` `PyYAML` `tqdm`。其中 `opencv-python` + `numpy` 占体积主要部分。
- C8 断点续跑依赖 `outputs/annotations.jsonl` 中 `generated_image` 字段推导出的 stem 集合（`_load_done`）。任何改变输出目录布局的方案都必须保持该文件语义不变，否则历史进度失效。
- C9 网络侧唯一依赖是 OpenAI 兼容中转站（`base_url` + `api_key`），无其他外部服务。
- C10 已核实项目仅使用 cv2 算法函数（`cvtColor` `GaussianBlur` `threshold` `morphologyEx` `getStructuringElement` `createCLAHE` `split` `merge`），无 `imshow` / `waitKey` / `VideoCapture` 等 GUI 调用。

## 4. 功能需求

### FR-1 单一安装包分发

- 1.1 交付物为 Windows 安装程序，安装后在开始菜单与桌面生成快捷方式。
- 1.2 目标机器无需预装 Python、pip、编译器或 VC++ 运行库之外的任何组件。
- 1.3 安装包不包含缺陷库与数据集；安装包体积 <= 120 MB，安装后占用 <= 300 MB。
- 1.4 程序显示版本号，且版本号与 git tag 一致。

### FR-2 冻结环境下的路径与配置基准

- 2.1 区分“安装根目录”（只读）与“工作区”（可写），见第 8 节。
- 2.2 `config.yaml`、`outputs/`、`logs/`、缺陷库均以工作区为基准解析。
- 2.3 改造完成后，源码方式运行现有 11 个 CLI 子命令的行为与当前完全一致（回归验证项）。

### FR-3 配置与密钥管理

- 3.1 配置分层，优先级由低到高：打包内置默认值 → 工作区 `config.yaml` → 用户配置文件 → 环境变量 → 界面本次运行的覆盖项。
- 3.2 API key 不得写入 `config.yaml`，也不得以任何形式嵌入可执行文件（exe 内的明文字符串可被直接提取）。
- 3.3 key 通过 Windows 凭据管理器加密保存在当前用户名下，界面输入框掩码显示。
- 3.4 保留 `RELAY_API_KEY` / `RELAY_BASE_URL` 环境变量通道，保证现有习惯与自动化脚本不被破坏。
- 3.5 界面提供“测试连接”，复用现有 `test-api` 逻辑，并明确提示该操作会消耗少量额度。

### FR-4 数据与缺陷库的外置管理

- 4.1 缺陷库作为独立数据包分发，程序启动时校验完整性（条目数、裁剪图缺失数），复用 `inspect` 的检查逻辑。
- 4.2 界面以目录选择器指定“无缺陷样本”根目录，消除全角括号与相对层级的手工约定。
- 4.3 选定目录后立即扫描并展示识别到的类别及每类图片数；扫描不到时给出可执行的修复提示，而不是仅报“类别无干净图”。
- 4.4 缺陷库分发前归一化 `catalog.json` 的 `source_image` 为相对路径（对应 C5）。

### FR-5 任务执行与可观测性

- 5.1 界面可配置并启动 `gen-target`（主命令）：选择类别、数量、是否 `--force`。
- 5.2 实时展示总进度、已完成/合格/驳回/失败计数、当前并发数、预计剩余时间。
- 5.3 实时日志视图，支持按级别过滤与一键打开日志目录。
- 5.4 可随时请求停止；停止为优雅停止（不再派发新任务，等待在途任务落盘），保证 `annotations.jsonl` 不被截断。
- 5.5 断点续跑语义与现有实现一致（跳过已完成 stem），界面在启动前显示“将跳过 N 项、待生成 M 项”。
- 5.6 运行日志落盘到 `logs/`，按大小轮转；`outputs/fail_log.jsonl` 保持现有格式不变。
- 5.7 失败原因分类统计（现 `fail-summary`）以界面面板呈现。
- 5.8 关闭界面窗口不中断正在执行的生成任务；重新打开界面可重新附着并继续观察进度。

### FR-6 成果导出

- 6.1 一键导出压缩包，内容为 `generated/`、`rejected/`、`annotations.jsonl`。
- 6.2 强制排除 `debug/`、`debug_preview/`、`seg_preview/` 等中间产物。
- 6.3 导出前展示预估体积与文件数并要求确认。

### FR-7 保留 CLI

- 7.1 打包后的程序保留完整 CLI 入口，参数与现有 `run.py` 一致，便于脚本化与排障。
- 7.2 CLI 模式下中文输出不乱码（对应 C6）。

### FR-8 可复现构建

- 8.1 依赖版本锁定（精确版本，非范围）。
- 8.2 一条命令完成“清理 → 打包 → 生成安装包”，构建脚本纳入版本控制。
- 8.3 构建脚本在打包后自动执行冒烟验证（启动 + `selftest`）。

## 5. 非功能需求

- NFR-1 行为等价：同一输入 + 同一配置 + 同一随机种子，封装前后产出的判定结果一致。这是本次改造的第一优先级验收标准。
- NFR-2 安全：不内嵌任何凭据；日志与界面不回显 key 明文（仅显示后 4 位）；崩溃报告不携带 key。
- NFR-3 稳定性：4 小时以上连续运行不因界面层泄漏内存而崩溃；日志无界增长受轮转约束。
- NFR-4 可维护性：核心流水线不依赖界面层；界面层与 CLI 层共用同一套核心 API。
- NFR-5 可诊断性：任一失败都能从日志定位到类别、任务 stem、失败分类三要素。
- NFR-6 可访问性：界面控件可键盘到达并具备可访问名称，文本与背景对比度符合 WCAG AA。完整符合性需人工配合辅助技术验证。

## 6. 验收标准

1. 在一台未安装 Python 的干净 Windows 机器上完成安装并成功生成至少 10 张样本。
2. 全程未设置任何环境变量。
3. 数据目录通过界面选择，目录名不受全角括号约束。
4. 中断后重启，界面正确显示跳过数量并接续生成，`annotations.jsonl` 无重复与损坏。
5. 一键导出的压缩包内容符合 FR-6，不含 `debug/`。
6. 源码方式运行原有 11 个 CLI 子命令，行为与改造前一致。
7. 从干净仓库执行构建命令，产出可安装的安装包，且冒烟验证通过。

## 7. 已确认决策

- D1 界面形态：原生桌面 GUI，且明确要求观感现代。
  据此选定 PySide6（Qt for Python）而非 Tkinter。Tkinter 虽零依赖，但无法满足观感要求，且长列表/表格性能不足。代价是包体增加约 50 MB。
  连带约束：`opencv-python` 必须替换为 `opencv-python-headless`。前者自带 Qt5 插件，与 PySide6 的 Qt6 在冻结后会争抢 `platforms/qwindows.dll` 导致启动失败。依据 C10，替换无功能影响。

- D2 缺陷库分发：独立数据包 + 引导解压。
  分发 `catalog-data.zip`，首次启动由界面引导解压到用户选定的工作区。打包前归一化 `catalog.json` 的 `source_image` 为相对路径。

- D3 回归测试：本阶段不做，待 GUI 与缺陷库外置完成后再评估。
  本阶段以 `selftest` + `inspect` + 逐命令输出对比作为“行为等价”的验证手段。
  已知缺口：这不足以证明 NFR-1，遗留为技术债，见第 9 节。

## 8. 工作区（因 D1/D2 引入的新概念）

安装目录（`C:\Program Files\...`）对普通用户不可写，而本项目的产物体积很大（`debug/` 约 2 GB，`generated/` 可达数十 GB）。
因此必须把“程序安装位置”与“数据存放位置”分离。

- 8.1 安装根目录（只读）：exe 与内置资源所在目录。
- 8.2 工作区（可写，由用户指定，应位于大容量磁盘）：包含 `config.yaml`、`catalog/`、`outputs/`、`logs/`。
- 8.3 工作区路径持久化在用户配置（`%APPDATA%` 下），首次启动由界面引导创建。
- 8.4 兼容性要求：源码方式运行且未设置工作区时，工作区默认等于仓库根目录，行为与改造前完全一致。
  该设计使 `Config.resolve()`（相对 `config.yaml` 所在目录解析）的语义无需改动，也使 `annotations.jsonl` 的路径语义（C8 断点续跑依赖）保持不变。

## 9. 技术债与遗留项

- TD-1 无自动化测试（D3 推迟）。“行为等价”当前仅靠人工比对验证。
- TD-2 `catalog.json` 的 `source_image` 绝对路径归一化只在打包环节做，仓库内的原始文件未修正。
- TD-3 `build-catalog` 未纳入界面（属非目标 N2），仍需通过 CLI 执行。
- TD-4 仅支持 Windows 分发（N4）。

## 10. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| `print` 改为统一输出边界时漏改或改错，导致关键诊断信息丢失 | 中 | 保留 print 兜底通道；改造后逐命令跑一遍对比输出 |
| PyInstaller 打包 `opencv-python-headless` / `numpy` 出现隐式导入缺失 | 中 | `.spec` 中显式声明 hiddenimports；构建后跑 `selftest` 冒烟验证 |
| 冻结路径改造影响 `_load_done` 的 stem 推导，历史进度失效 | 高 | 保持 `annotations.jsonl` 路径语义；用现有 jsonl 做续跑回归 |
| 优雅停止实现不当造成 `annotations.jsonl` 写坏 | 高 | 停止只停派发，落盘写入沿用现有 `ann_lock`，不引入新写入路径 |
| 界面层持有大图对象导致长跑内存增长 | 中 | 界面只传路径与统计，不持有 PIL 对象 |
| `opencv-python` 的 Qt5 插件与 PySide6 的 Qt6 冲突，冻结后启动崩溃 | 高 | 改用 `opencv-python-headless`；`.spec` 中排除多余 Qt 模块 |
| 用户把工作区设在系统盘导致空间耗尽（产物可达数十 GB） | 中 | 选择工作区时展示所在磁盘可用空间，低于阈值时告警 |
| PySide6 缺少 Qt 插件目录导致 “could not load the Qt platform plugin” | 中 | onedir 模式打包 + 构建后冒烟启动验证纳入构建脚本 |
