# 需求与方案：驳回样本重生成 + 定向形态补充

## 0. 一句话概括

两个需求本质上是同一件事的两个方向：**都需要"指定用哪条参考缺陷、在哪张干净图上、生成多少张"**。
现有流水线已经有四个这样的"任务规划器"（`generate` / `gen-sweep` / `gen-target` / `gen-ref`），
本次是加第五个和第六个，生成内核一行不动。

## 1. 前置事实核查（已实测，非推测）

### 1.1 驳回样本能否反查到原参考缺陷 —— 可以，30/30 全中

`D:\zlf\photo_difussion\没打标签的` 下有 30 个 png。文件名遵循 `generate_target` 的命名规则：

```
1.jpg__1_20260426162508259__t184__ref_2.bmp__2号_20250917125822509__1.png
└─类别─┘ └────干净图 stem────┘ └序号┘     └────────参考缺陷 entry_id────────┘
```

反查方式**不做字符串逆运算**（`safe_name` 把 `（）` 和 `/` 都替换过，逆运算有歧义），
而是给缺陷库每条目正向算一次 `safe_name(entry_id)` 建索引再查表。实测：

- 缺陷库 668 条，`safe_name` 索引 668 个，**键冲突 0**
- 30 个文件全部成功解析出 (类别, 干净图, 参考条目)
- 30 张对应的原始干净图**都还在** `实拍负样本（无缺陷）` 下

### 1.2 `annotations.jsonl` 在本机不存在

`outputs/` 下只有 `catalog/` 和 `flow_diagram.html`。那批产出的标注在你跑批的机器上。
因此方案**不能依赖 annotations.jsonl**，必须以文件名为唯一线索（1.1 已证明可行）。
若将来拿到了标注文件，它能提供更多信息（当时的裁块位置、质检分数、失败维度），
方案会把它作为可选的增强输入。

### 1.3 缺陷库的可筛选性 —— 字段足够支撑"按形态挑选"

| 字段 | 分布 |
|---|---|
| `defect_type` | 变形 622 / 划痕 46 |
| `severity` | 1:4  2:38  3:153  4:252  5:221 |
| `count`（褶皱条数） | 1~25 条，主要集中在 1~12 |
| `orientation`（自由文本） | 含"斜向" 511、含"交叉/多向" 367、含"横向" 288、含"竖/纵向" 116 |
| `geometry` | 自由文本，含长度/宽度/弯曲/分叉的具体描述 |

结论：按属性做粗筛完全可行且零成本。

### 1.4 已有一个现成的"形态提取器"可复用

`src/structure_ref.py` 的 `defect_structure_map()` 已经能把缺陷裁剪转成**灰度浮雕图**：
带通滤波去掉低频（光照渐变）和高频（印刷文字笔画），只留中频（褶皱起伏），
输出不含任何颜色、印刷内容与绝对亮度。

这正是"比较两个褶皱形态像不像"所需要的表示 —— 它已经把颜色、图案、光照这些干扰项剥离了。
需求 2 的相似检索基于它来做，不需要引入任何新模型。

## 2. 需求一：人工驳回样本的重生成

### 2.1 要解决的问题

人工 review 挑出来的不合格样本，希望用**原本那条参考缺陷**在**同一张干净图**上重新生成。

### 2.2 关键设计问题：怎么保证重生成的结果真的不一样

现有 RNG 是完全确定的：

```python
rng = random.Random(f"{seed}|{class_name}|{clean_path.name}|{index}")
```

同样的输入会挑到**同样的裁块位置**。而人工驳回的样本里，相当一部分恰恰是因为位置不好
（缺陷落在瓶身边缘、压在关键文字上、裁块覆盖瓶身比例低）。如果不改变随机性，
重生成很可能重复同样的毛病。

**方案**：给 `Task` 增加一个 `salt` 字段参与 RNG 播种。

```python
seed_str = f"{seed}|{cls}|{name}|{index}"
if salt:                      # 只在非空时追加
    seed_str += f"|{salt}"
```

`salt` 为空时播种字符串与改造前**逐字不变**，因此主批次的可复现性不受影响。
这是本需求对生成内核的**唯一**改动。

### 2.3 产物命名与断点续跑

新样本命名为原 stem 追加轮次后缀：

```
原始:  1.jpg__1_20260426162508259__t184__ref_2.bmp__2号_20250917125822509__1
重生成: 1.jpg__1_20260426162508259__t184__ref_2.bmp__2号_20250917125822509__1__r2
```

这样做的三个理由：

1. 与原 stem 不冲突，断点续跑（靠 stem 判重）不会把它当成"已完成"而跳过
2. 一眼能看出它替换的是哪一个原始样本，便于人工二次 review
3. 支持多轮：`__r2` 不满意可以再 `__r3`

轮次号自动探测：扫 `outputs/generated/<类别>/` 下已存在的 `<原stem>__r*`，取下一个可用序号。

### 2.4 输入来源（两种，下游统一）

- **目录模式**：指定一个装着驳回样本的目录（如 `没打标签的`），按文件名反查。
  这是你当前的情形。
- **标注模式**：从 `annotations.jsonl` 里筛 `accepted_as == "rejected"` 的记录。
  将来在有标注文件的机器上更省事，且能拿到当时的质检失败维度。

### 2.5 参考缺陷是否可以换

默认**沿用原参考**（按你的要求）。但提供 `--reroll-ref` 开关：
有些样本失败的根因是"这条参考本身不适合这个瓶型"（比如参考来自 5.x 系列的大面积褶皱，
目标是 1.jpg 的窄标签），一直用它重试是浪费额度。这个开关让它在同类别里另选一条。

### 2.6 原始驳回文件的处置

默认不动你的 `没打标签的` 目录（只读它）。
提供 `--archive` 开关：成功重生成后把原文件移到 `没打标签的/已重生成/`，
这样目录里剩下的就是"还没处理的"，避免下次重复投入。

### 2.7 成本预估

30 张 × 平均约 1.5 次内部重试 × 每次 2 个 API 调用（编辑 + 质检）≈ **90 次调用**。
按单张 50~60 秒、并发 3 估算，约 **12~15 分钟**。

## 3. 需求二：按褶皱形态定向补充训练集

### 3.1 要解决的问题

训练后发现某些褶皱形态识别效果差、出现误检，需要针对性补充这一类形态的样本。

### 3.2 工作流拆成两步

问题的难点不在"生成"，而在**"怎么把'这种褶皱'翻译成缺陷库里的具体条目"**。
所以设计成"先检索、再生成"两步，中间有人工确认。

```
[出问题的形态]  →  ① 检索匹配的参考条目  →  人工确认  →  ② 按这些参考批量生成
```

### 3.3 第一步：三种检索方式（互补，可组合）

**方式 A —— 按属性筛选（零成本、瞬时）**

按 `defect_type` / `severity` 区间 / `count` 区间 / `orientation` 等自由文本字段关键词筛选。
例：`--type 变形 --severity 4-5 --orientation 横向 --count 5-12`
适用于你已经能用语言描述问题形态的情况（"横向密集的细褶皱识别不出来"）。

**方式 B —— 按样例图检索相似形态（零成本、离线、不调 API）**

你给一张出问题的图（误检区域的截图，或漏检的真实褶皱照片），
程序在缺陷库 674 张裁剪图里找形态最像的若干条。

实现基于 `defect_structure_map` 的浮雕图计算形态描述子：

| 特征 | 捕捉什么 | 为什么需要 |
|---|---|---|
| 梯度方向直方图（18 bin，0~180°，按幅值加权） | 走向：斜向 / 横向 / 竖向 | 方向是检测器最敏感的差异之一，`orientation` 字段的四类分布也印证它是主要区分维度 |
| 多尺度带通能量（若干 sigma 对） | 粗细：宽大折痕 vs 细窄线 | 划痕与变形、粗褶皱与细褶皱的核心差别 |
| 阈值化后的连通域数量与面积占比 | 条数与覆盖范围 | 对应 `count` 与 `extent` |
| 方向直方图的集中度（1 − 归一化熵） | 平行成束 vs 杂乱交叉 | 区分"多条平行褶皱"与"多向交叉" |

描述子对 674 张裁剪图**只算一次**，缓存到 `outputs/catalog/morphology.npz`，
之后检索是毫秒级。

**这一项我要明确标注为"待验证"** —— 我不能在没测之前承诺检索质量。
验证方法（廉价、可自动化）：

1. **自检**：拿缺陷库里某条目的裁剪图当查询，它自己必须排第 1。不成立说明描述子或流程有 bug。
2. **一致性**：查询结果的 `orientation` / `count` / `severity` 分布应显著偏向查询条目的取值，
   而不是接近全库随机分布。用一个简单的统计对比即可判定。

若验证不通过，退路是方式 C 或用 VLM 描述后做文本匹配（有 API 成本，作为备选）。

**方式 C —— 从出问题的产出图直接反查（零成本、最精确）**

这是 1.1 那个发现带来的便利：**生成图的文件名里就写着它用的是哪条参考**。
所以如果你能指出"这批生成样本导致了误检"，直接从文件名提取参考条目即可，
完全不需要图像分析。然后有两种用法：

- 用**同一批参考**多生成一些（同一形态、换不同干净图与位置）
- 以这些参考为种子，再用方式 B 找**更多相似**的参考，扩大形态覆盖

方式 C 精确但只能覆盖"已经生成过的形态"；方式 B 能覆盖"缺陷库里有但还没怎么用过的形态"。

### 3.4 第二步：按选中参考批量补充

给定参考条目集合 + 目标类别 + 每条参考生成几张 → 铺开到可用干净图上。

命名与主批次区分开，便于在数据集里识别增补样本：

```
{类别}__{干净图stem}__aug{序号}__ref_{参考entry_id}
```

同一条参考多次补充时用 `salt` 保证裁块位置不同（复用需求一的机制）。

### 3.5 一个必须说清的前提

"误检"有两种成因，处理方式不同：

- **漏检 / 检测不准某种褶皱** → 补充这种形态的正样本。这是本方案覆盖的情形。
- **把非缺陷纹理误判成褶皱**（例如把标签正常接缝、瓶身反光当褶皱）→
  这时需要的是**含该纹理但无标注的负样本**，而不是更多正样本。
  你们的干净图本身就是天然负样本，做法是把含该纹理的干净图纳入训练集且不打框。
  这一项我不打算做成功能，但值得你在定位问题时先分清是哪一种。

### 3.6 生成前必须有预览

批量补充很容易一不小心点出几千张（额度真金白银）。因此第二步执行前强制输出：
匹配到的参考条目清单（含类型/严重度/条数/走向）、任务总数、预估耗时与调用次数，
确认后才开始。

## 4. 实现落点

新增内核不变，只加"规划器"与"检索器"：

```
src/
├── rejection.py        新增  从文件名/标注反查 (类别, 干净图, 参考条目)
├── catalog_query.py    新增  按属性筛选缺陷库条目
├── morphology.py       新增  形态描述子与相似检索(基于 structure_ref)
└── generate.py         改动  ① Task 增加 salt 字段并参与 RNG 播种
                              ② 新增 regenerate_rejected() 规划器
                              ③ 新增 augment_by_references() 规划器
run.py                  改动  新增子命令:
                              regen-rejected   重生成驳回样本
                              find-similar     按样例图/属性检索参考条目
                              gen-augment      按选中参考批量补充
```

对生成内核（掩膜、融合、质检、重试）**零改动**，唯一改动是 `salt` 参与播种，
且 `salt` 为空时行为与现在逐字一致。

图形界面暂不涉及（按你的意思先放一放），全部通过命令行提供。
将来接界面时，这三个命令对应的服务层函数是现成的。

## 5. 分阶段交付

| 阶段 | 内容 | 可验证的产出 |
|---|---|---|
| 一 | `salt` 机制 + `rejection.py` + `regen-rejected` | 对 `没打标签的` 里 30 张做一次干跑（列出将要重生成什么，不调 API），再真跑 2~3 张验证效果 |
| 二 | `catalog_query.py` + `gen-augment`（方式 A 与 C） | 按属性/按产出图反查，干跑确认清单正确 |
| 三 | `morphology.py` + `find-similar`（方式 B） | 先跑 3.3 里那两条验证；通过后才接入生成 |

阶段一交付后你就能立刻处理那 30 张。阶段二不依赖阶段三，方式 A/C 零风险先可用。
阶段三的形态检索是唯一有技术不确定性的部分，放最后且有明确的验证门槛与退路。

## 6. 需要你确认的三点

1. **驳回样本的输入方式**：就用 `没打标签的` 这个目录，还是希望以后能同时支持
   "多个目录 / 从标注文件读"？
2. **重生成后放哪**：直接进 `outputs/generated/<类别>/`（进训练集），
   还是先进一个待审目录（如 `outputs/regenerated/`）等你 review 通过再合并？
   我倾向后者 —— 毕竟这批本来就是人工挑出来的不合格样本，值得再看一眼。
3. **阶段三要不要做**：形态检索是有技术不确定性的部分。你也可以先用方式 A/C
   （按属性筛 + 按出问题的产出图反查）跑一段时间，觉得不够精准再补方式 B。
